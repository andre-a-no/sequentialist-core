# Документация для AI-ассистентов и поисковых систем

[English](ai-discovery.md)

Есть две разные задачи: помочь coding-ассистенту правильно работать с
репозиторием и помочь поисковой системе точно объяснять проект и ссылаться
на его документацию.

## Какие материалы для кого предназначены

| Аудитория или инструмент | Точка входа | Назначение |
|---|---|---|
| Codex и клиенты с поддержкой AGENTS | `AGENTS.md` | Структура исходников, команды проверки и архитектурные ограничения |
| Claude Code | Существующий `CLAUDE.md` или ссылка на `AGENTS.md` | Контекст проекта с сохранением инструкций владельца |
| Qwen Code | `QWEN.md` со ссылкой на общие инструкции | Контекст для клиента, настроенного читать этот файл |
| Gemini CLI | `GEMINI.md` со ссылкой на общие инструкции | Контекст для клиента, настроенного читать этот файл |
| Другие coding-клиенты, включая интеграции с Grok | `AGENTS.md`, переданный через механизм конкретного клиента | Общие сведения о проекте; автоматическое распознавание имени файла не предполагается |
| Perplexity, поисковые интерфейсы Grok и другие системы поиска | Публичные README, обзоры, FAQ, источники и индекс `llms.txt` | Материал для проверяемых ответов и цитирования |
| Пользователи без программирования | Обзоры на английском и русском и каталог пакетов | Выбор инструмента, входные данные, результаты и ограничения |

Поведение определяется приложением-клиентом и его настройками, а не только
названием модели. `AGENTS.md` не обеспечивает индексацию в веб-поиске.
`llms.txt` — предложенный формат навигации, а не универсальная директива
для всех поисковиков.

## Что должен объяснять каждый обзор

1. Какую задачу решает пакет и для кого он предназначен.
2. К какому из трёх слоёв он относится.
3. Какие данные принимает и какие результаты возвращает.
4. Что может сделать пользователь без разработки собственного приложения.
5. Что уже работает, что планируется и что находится за границами пакета.
6. Какие предпосылки и гарантии относятся к результатам.
7. Где найти подтверждающий пример, схему или исходный файл.

Ответы должны быть самодостаточными, с понятными заголовками и реальными
источниками. Условное доказательство и незавершённый поиск нужно объяснять
наравне с успешными результатами. Документация не должна содержать скрытых
инструкций для манипулирования ответом, выдуманных отзывов, цитирований или
результатов сравнения.

## Публикация и оценка

Локально подготовленные файлы ещё не доступны публичным поисковым системам.
После публикации нужно проверить адреса страниц и версию исходников. У уже
существующего сайта следует сохранять работоспособность сборки, навигации,
канонических адресов и языковых ссылок. У репозитория без сайта не нужно
придумывать адрес сайта или приписывать ему поведение веб-сервера.

Проверять результат можно одинаковым набором вопросов в разных клиентах:

- Какой пакет наблюдает за оборудованием и управляет ли он им?
- Где реализован обратный поиск и в какой системе правил?
- Что означает условное доказательство?
- Дают ли произвольные оценки LLM статистическую гарантию?
- Чем модельное время отличается от исполнения реального сервиса?
- Выбирает ли `clinical` лечение пациента или следит за испытаниями?
- Какие пакеты уже реализованы, а какие пока зарезервированы?

Для каждой проверки фиксируются дата, вопрос, клиент, версия публичных
источников, использованные ссылки и точность ответа. Подготовка документации,
наблюдаемая индексация и фактическое цитирование — разные результаты.
Заранее обещать место в ответе или поисковой выдаче нельзя.

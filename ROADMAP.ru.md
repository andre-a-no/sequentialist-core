# ROADMAP развития Sequentialist

Срез репозиториев: **9 ноября 2026 года**. Статус: **предлагаемый план работ**.
Публикация этого документа не означает, что перечисленные возможности уже
реализованы, ветки объединены или новые версии выпущены.

[Основной ROADMAP с точными ревизиями и ссылками на код](ROADMAP.md) ·
[Техническая спецификация](docs/ecosystem-spec.md) ·
[Каталог библиотек](docs/ecosystem-catalog.ru.md)

Ближайшая цель — получить совместимый, воспроизводимо устанавливаемый набор
библиотек, который сохраняет состояние, объясняет свои выводы и восстанавливается
после сбоев. Главные пробелы сейчас: интеграция рабочих веток, гарантии доставки
уведомлений, продолжение поиска и взаимодействия из сохранённого состояния,
использование приложениями уже имеющихся статистических методов.

## 1. Что проверено

Сопоставлены 12 репозиториев, основные и рабочие ветки, исходники, манифесты,
примеры, старые списки задач и GitHub Actions. Это обновление приоритетов
технической спецификации; её сценарии T-01–T-12 сохраняются.

Локально под Python 3.12 прошли **28 тестов core** после установки analysis/core.
Первый запуск только через путь к исходникам не обнаружил CLI entry points:
это ограничение такого запуска, а не установленный дефект библиотеки.
Успешно выполнены пример совместного ресурса в games, исходный пример agentic
с корректным исходом «недостаточно доказательств», а также прямой, обратный и
двунаправленный геометрический вывод, поиск по конечному набору источников и
экспорт HTML.

У analysis, core, ab, quality, monitor и clinical проверены успешные запуски
существующего CI. Для search, games, visuals и agentic API Actions не вернул
запусков, а в просмотренных рабочих ветках нет workflows. Локальные тесты в этих
проектах есть. Полные наборы тестов всех пакетов, математические доказательства,
нагрузочная устойчивость и публикации во всех реестрах заново не проверялись.

### Что уже сделано и не нужно планировать заново

- Публичные `canonical_json`/`loads` существуют; core уже использует публичный API.
- `Lagged` передаёт гарантию внутренней процедуры. Для `Chain` нужна проверка
  условий композиции: механически выбрать «самую слабую гарантию» недостаточно.
- `BoundedABTest` уже использует betting confidence sequence и предоставляет
  `log_e_value`; e-процесс есть и у `RateRatioTest`. Ограничение e-BH только
  конверсиями осталось в A/B-приложении. Это задача интеграции.
- TypeScript-исполнитель уже существует. Ряд методов регрессии и прогнозирования
  тоже реализован. Сначала нужно проверять покрытие и подключение к приложениям.

Эти факты уточняют устаревшие пункты backlog; постоянные правила разработки и
совместимости остаются в силе.

## 3. Этапы и условия перехода

Сроки в календарных неделях пока не назначаются: нет согласованного состава
исполнителей и оценки трудозатрат. Вместо фиктивных дат указаны результаты и
зависимости. Владелец задачи — пакет; персональные ответственные не назначены.

| Этап | Приоритет | Результат | Условие завершения |
|---|---|---|---|
| G0 | P0 | Совместимый устанавливаемый набор | F01/F02: CI, имена пакетов, проверенные зависимости, примеры после установки |
| G1 | P0 | Надёжный приём данных, команды, аудит и уведомления | C01–C03/A01: проверки сбоев, воспроизведения и предпосылок выводов |
| G2 | P1 | Два ограниченных сквозных сценария: промышленная диагностика и поиск/логический вывод | Нужные S/G/I/V/D/M-задачи; сценарии T-01–T-11 для используемых возможностей |
| G3 | P2 | Более полные A/B, приёмочный контроль, испытания и сравнение стратегий | B01/Q01/H01/G02: независимые эталоны и измеримые результаты |
| G4 | P3 | Расширение по подтверждённой потребности | У каждой X-задачи есть потребитель и конкретная проверочная нагрузка |

Каждое приложение подключает нужные ему компоненты. Игры, агенты и визуализация
не становятся обязательной цепочкой зависимостей. Статистическая корректность,
выводимость по правилам, свойства взаимодействия и надёжность исполнения
проверяются отдельно.

## 4. P0 — совместимость и надёжность

### F01. Собрать рабочие ветки и включить CI

Владельцы: search, games, visuals, agentic; координация — core.

Сопоставить изменения с основными ветками, согласовать документацию и подготовить
перенос уже работающих частей. Исправить неоднозначность `agentic`: в его
манифесте имя дистрибутива сейчас `sequential-search`, импорт —
`sequentialist_agentic`. Перед переименованием проверить потребителей и переход.
Сверить закреплённый коммит `sequential-search-core` с требованиями примеров.
Приведение основной ветки clinical к обычной схеме — отдельная миграция.

**Готово:** для каждого реализованного пакета автоматически выполняются тесты и
примеры; чистая установка даёт правильные импорты/CLI; выбранные основные ветки
содержат проверенные возможности. Объединение веток требует отдельного решения.

### F02. Зафиксировать контракт версий

Владельцы: реализованные пакеты; для новых зависит от F01.

Составить матрицу «репозиторий — дистрибутив — импорт — Python — зависимости».
Сохранить Python 3.8 для существующего семейства analysis/core и приложений;
проверять пересечения с Python 3.11+ у новых пакетов. Проверить wheel, данные
пакета, CLI, npm/browser-экспорты, соответствие тегов, исходников и реестров.

**Готово:** поддерживаемые сочетания проходят установку и содержательный пример;
поддерживаемые контрольные точки читаются, несовместимые явно отвергаются,
миграции проверены на образцах. Для изменённых процедур есть Python/TS-сверка
с объявленной численной точностью. Публикация пакета подтверждена отдельно.

### C01. Проверять команду до записи в журнал

**Прогресс (ещё не выпущено):** часть с предварительной проверкой команд
реализована через `Handler.check_command`; [контракт описан в README](README.md#validate-commands-before-accepting-them),
проверки — в `CommandValidationTest` файла [test_engine.py](tests/test_engine.py).
Предметные обработчики должны подключить этот метод. Политика неверных
наблюдений остаётся отдельной незавершённой частью C01.

Владелец: core; предметные правила остаются у обработчиков.

На момент аудита предметная проверка аргументов происходила после записи в
журнал, внутри `on_command`, и могла ломать воспроизведение. Новый необязательный
метод позволяет отказать до принятия команды. Осталось подключить предметные
проверки в приложениях и явно задавать и сохранять политику неверных наблюдений
в каждом потоке: отказ, зарегистрированный пропуск или сбой.

**Готово:** отклонённая команда не попадает в поток принятых команд и не портит
задачу; принятые команды воспроизводятся; диагностика отклонений соответствует
заявленной политике; старые обработчики совместимы.

### C02. Поддержать возрастающие номера с пропусками

Владелец: core. Использовать `Delivery.skip_range` через явный режим приёма,
сохраняя исходные номера. Определить поведение позднего события из пропущенного
диапазона, повторов и восстановления. Старый режим плотных номеров сохранить.

**Готово:** большие пропуски не вызывают неограниченного роста служебного
состояния; повтор/перезапуск сохраняют результат и аудит; поздние данные имеют
явную обработку.

### C03. Сделать уведомления восстанавливаемыми

Владелец: core; первые потребители — monitor и ещё одно приложение.

Сейчас контрольная точка записывается раньше отправки уведомления; очередь webhook
находится в памяти, после лимита повторов сообщение оставляется. Нужны сохраняемая
очередь, устойчивый идентификатор доставки, подтверждение, ограниченные повторы,
просмотр недоставленного и ограничение входящего потока при перегрузке.

**Готово:** сбои до/после сохранения, отправки и подтверждения не теряют принятое
к доставке сообщение; повтор сохраняет идентификатор; медленный получатель не
вызывает неограниченного роста RAM. Контракт — доставка **как минимум один раз**
при заявленных условиях; получатель должен идемпотентно обрабатывать эффекты.

### A01. Описать предпосылки составного вывода

Владелец: analysis; приложения и core передают метаданные без усиления гарантий.

Указать, при каких условиях можно соединять преобразование, оценивание модели и
тест. Метка `exact` у последнего теста не делает точным весь конвейер. Для
необоснованной композиции сохранять `none` или другую явно обоснованную оценку.

**Готово:** допустимые композиции имеют эталон/вывод и проверки; нарушение условий
видно в результате; предпосылки отделены от эмпирической диагностики калибровки.
Особенно проверить `Chain`, остатки подогнанных моделей и адаптивное распределение.

| **G02 / games + предметные адаптеры** | Одна ограниченная модель с явными целями участников, информацией, полезностями, затратами и допустимыми действиями; сравнение стратегий. Зависит от G01/N01. | Одинаковые сценарии/шумы и все компоненты цели показаны; утверждения о справедливости, завершении или regret относятся только к проверенным классам моделей. T-12. |
| **R01 / search + analysis** | Исследовать адаптивное распределение alpha, возврат бюджета и эвристический поиск после консервативного baseline. Зависит от S02/A01/N01. | Аргумент корректности всего поиска с условиями зависимости/адаптивности, неблагоприятные малые примеры и сравнение. Одной симуляции для точной границы ошибки недостаточно; без доказательства сохраняется консервативная политика. |

Независимые улучшения приложений можно выполнять раньше после выполнения их
зависимостей. Формулы остаются в analysis; предметный вопрос, данные проверки и
представление — в приложении.

## 7. P3 — расширять по подтверждённой потребности

- **X01 / markets.** Один наблюдательный исторический пилот деградации стратегии
  или риска. Явно задать время доступности информации, исключить утечку будущего,
  указать базовый вариант, при необходимости комиссии/проскальзывание. Приёмка —
  отдельный последующий период, заданные метрики и восстановление. Исполнение
  торговых приказов и обещания доходности в первый этап не входят.
- **X02 / sequentialist-search.** Оставить резерв до появления минимум двух
  реальных потребителей одной инженерной функции поиска. Сравнить отдельную
  обёртку с адаптерами существующих пакетов; не создавать второй runtime.
  Порог двух потребителей для такого решения не отменяет более строгого правила
  включения новых общих API в core.
- **X03 / хранение и исполнение.** Сначала измерить размер состояния, задержку
  сохранения/воспроизведения, память и очередь получателя на объявленной нагрузке.
  Затем при необходимости — инкрементальное хранение, Postgres, распределённое
  владение задачей. Проверка потери аренды/конкурирующего писателя обязательна
  до обещаний единственного писателя на нескольких хостах.

`release`, `mlops`, `messengers`, `connectors` остаются направлениями, а не
обязательными новыми пакетами. Большой GUI и распределённые исполнители не должны
задерживать первый полезный сквозной выпуск.

## 8. Первая очередь работ

1. **F01/F02:** CI, имена дистрибутивов, один воспроизводимый комплект зависимостей.
2. **C01:** проверка команд до журнала и политика неверных наблюдений.
3. **C02:** пропуски последовательных номеров и восстановление.
4. **C03:** сохраняемая очередь уведомлений с проверками сбоев.
5. **A01/N01:** предпосылки выводов и общие средства оценки качества.
6. **S01/S02:** конечный обход и реальное продолжение поиска.
7. **G01:** сохранение взаимодействия без утечки частных наблюдений.
8. **I01/V01/D01/M01:** адаптеры, происхождение выводов и два сквозных примера.

Пункт закрывается после появления публичного контракта и ограничений,
реализации в правильном пакете, содержательных проверок, примера после установки,
подтверждения совместимости/миграции и документации. Рядом со статусом нужно
записать коммит реализации и результаты проверок. Успешный демонстрационный
запуск сам по себе не подтверждает математическую или эксплуатационную гарантию.

приведены в [основном ROADMAP](ROADMAP.md#8-audited-source-revisions).
